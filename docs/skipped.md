# 理解をスキップした範囲

後で振り返るための記録。CLAUDE.md の学習方針 4 に基づく。

## M0 ステップ1: CMake で空のプロジェクトを作る(2026-11-11)

理解できた: `build/` の中身は生成物で、消すと exe や .obj が失われる。

スキップした確認(「今回の本質ではない」として):
- `cmake --preset`(生成)と `cmake --build`(ビルド)が別の段階であること
- ソースやヘッダの追加は `CMakeLists.txt` の `add_executable` に書く。VS で `.vcxproj` に足しても、次の生成で上書きされて消える
- `/EHsc` を取り除いてから `/EHs-c-` を付ける理由(付けるだけだと、矛盾した指定が両方渡り、上書きの警告 D9025 が出る)

## M0 ステップ2: SDL3 を FetchContent で組み込む(2026-11-11)

理解できた: `target_link_libraries` を消すとビルドが通らない(ただし失敗するのはリンクより手前のコンパイルで、`SDL3/SDL.h` が見つからないため)。

スキップした確認:
- FetchContent は生成(configure)のときに SDL3 のソースを `build/_deps/` にダウンロードし、自分のプロジェクトの一部としてビルドする。NuGet と同じく「バージョンを書けば取ってきてくれる」が、ビルド済みのバイナリではなくソースを取ってきて手元でビルドする点が違う
- `target_link_libraries` は、ヘッダのインクルードパスとライブラリのリンクを、まとめて伝える

## J-3a: 型の名前からオブジェクトを作る(TypeRegistry)(2026-11-12)

「また後でしっかり理解したい」として、確認を後回しにした。

後で理解したいこと:
- C++ では、実行中に文字列(`"SpriteComponent"`)から型を作れない理由。C# は DLL に型の情報(メタデータ)が残っていて `Activator.CreateInstance` で作れるが、C++ はビルドするとほぼ機械語だけになり、「どの型を作るか(大きさ、どのコンストラクタを呼ぶか)」はコンパイルするときに決まっている必要がある
- `TypeRegistry` が覚えているもの: 名前と「その型を作る、コンパイル済みの関数」の組。`Register<T>()` の中のラムダ式が、型ごとにコンパイルされて、その関数になる(C# の `Dictionary<string, Func<Object>>` に近い)
- `HUSKY_OBJECT` で作る `TypeInfo`(型の名前、プロパティ)も、同じ理由で自前で用意している(C# なら最初からあるメタデータ)
- 自動登録(グローバル変数の初期化)を避けた理由: 静的ライブラリの中のものはリンカに捨てられることがある、初期化の順番が決まらない
  - 2026-11-12 に振り返った。理解できた: `Register<BouncerActor>()` を消すと、作る関数が見つからないので、その型のオブジェクトは作られない(シーンの読み込みは止まらず、警告を出して飛ばす)。テンプレートが型ごとに「作る関数」を生み、登録簿がそれを名前と組で覚える、という流れ。

## CAM-2: カメラのコンポーネント(2026-11-13)

理解確認の問題に答えず、Transform の相談に進んだ。

後で理解したいこと:
- カメラのアクターを右(+x)へ 100 動かすと、画面に映る世界は左へ 100 ずれて見える
- ビュー行列が「カメラの位置」ではなく「-位置」でずらす理由: ビュー行列は、世界の点を「カメラから見た位置」に直す行列。カメラが (100, 0) にいるなら、世界の (100, 0) がカメラから見て (0, 0)(画面の真ん中)になるよう、全部の点から 100 を引く。カメラを動かす代わりに、世界を逆へ動かしている

## TR-1: Transform を Actor のメンバーにする(2026-11-13)

理解確認の問題に答えず、次へ進んだ。

後で理解したいこと:
- Transform をコンポーネントではなく Actor のメンバーにしたことで、できなくなったこと: 「位置を持たないアクター」を作れない(ゲームの規則やマネージャのような、場所の無いものも位置を持つ)。また、Transform の種類を替える(例えば UI 用の別の Transform に差し替える。UE の SceneComponent の代わりに別の部品を根にする)ことができない。どのアクターも同じ形の Transform を必ず持つ

## CAM-3: カメラの追従(2026-11-13)

理解確認の問題に答えず、次へ進んだ。

後で理解したいこと:
- 追従の実行順を Default(プレイヤーと同じ)にすると、どちらが先に動くかがシーンの一覧の順で決まる。カメラが先だと、1 フレーム前のプレイヤーの位置を追うので、動いている間はプレイヤーが画面の真ん中から進む向きへ少しずれて見え、止まると真ん中に戻る(ぶれる)。Late にすれば、必ずプレイヤーが動いた後に追う

## PF-1: プレハブの読み書き(2026-11-13)

理解確認の問題に答えず、次へ進んだ(つながりの方針は C(違いだけを保存して反映)に決定)。

後で理解したいこと:
- プレハブから guid を外す理由: guid を残すと、同じプレハブを2回置いたとき2体が同じ guid になる。SceneSerializer::Read は重なりを見つけて後のほうに振り直し警告を出すが、置くたびに警告が出る。振り直さなければ、guid で指すコマンド(property.set、Undo の履歴)が別のアクターを書き換えてしまう。guid は「シーンの中のこの1体」の ID で、プレハブ(型紙)の値ではない

## PF-4 / PF-5: プレハブとの違いの保存、Apply / Revert(2026-11-13)

理解確認の問題に答えず、次のセッションへ進んだ。

後で理解したいこと:
- PF-4: ハンドルは、プレハブと同じでも毎回書く理由: ファイルの中のハンドルは「そのファイルの中の番号」で、シーンとプレハブでは番号の振り方が違う。同じ数でも別の相手を指しているかもしれず、比べても意味が無い。書かずにおくと、読むときにプレハブの中の相手(番号)を指してしまう
- PF-5: Apply の後、ほかのアクターには「プレハブの古い値のまま」の値だけを伝える理由: 古い値と違う値は、そのアクターが自分で変えた値(上書き)で、シーンに「違い」として保存されている。新しい値で上書きすると、その人が意図して変えた値が消えてしまう(Unity も同じ)。保存・読み込みで言えば、違いとして保存された値は、読むときにプレハブの値の上に重ねられるので、そもそもプレハブの変化に関係なく残る

## PF-6a: actor.destroy と、Undo で戻す actor.restore(2026-11-13)

理解確認の問題をスキップした。

後で理解したいこと:
- Undo の控えを、ポインタやハンドルではなく「シーンのファイルと同じ形の値(ArchiveValue)」で持つ理由: 消したアクターはフレームの終わりに FlushDestroyed で本当に無くなり、メモリは別のオブジェクトに貸し直される。ポインタは壊れたメモリを指し、ハンドルは世代が変わって何も指さなくなる。値の控えなら、アクターが無くなっても残るので、そこから同じ guid で作り直せる(読むのはシーンの読み込みと同じ道具なので、新しい読み書きのコードも要らない)

## SF-1 / SF-2a: 型の付いた参照 ObjectRef<T> と配列 std::vector<E> のシリアライズ(2026-11-13)

ユーザーが「シリアライザ周りは難しいので、一通り落ち着いたら復習する」と決めた。理解確認はどちらも「分からない」で、説明は済み。

後で復習したいこと:
- ObjectRef<T> の中身を T によらず同じ ObjectReference(ハンドル1つ)にする理由: シリアライザ・GC・インスペクタは T を知らずに1つの道(GetValuePtrAt<ObjectReference>)で扱える。T の違いは Property の型の情報(GetObjectRefType。ただの値)として持つ。C++ のテンプレートは実行中にまとめて扱えず、スクリプトは実行中にテンプレートを作れないため(AssetRef<T> と AssetReference も同じ)
- ArrayInfo が関数のポインタ(大きさ、大きさを変える、i 番目の場所、消す)を持つ理由: シリアライザはエンジンの中で1回だけコンパイルされ、ゲームがどの std::vector<E> を使うかを知らない。型を知っている HUSKY_PROPERTY の場所(ArrayInfoOf<T>)で E 専用の関数を作り、ポインタを Property に渡す。シリアライザは渡された関数と要素1つのプロパティ(element。オフセット 0)を使うだけ
- 読み込みで ObjectRef の相手の型を確かめる流れ(ObjectSerializer が Object::GetOwnerRegistry で相手を引き、IsA で比べる。違えば null + 警告)

## PHY-2a 以降: 物理(Rigidbody2D と体の同期)(2026-11-14)

ユーザーが「物理も後から復習する」と決め、理解確認をスキップした。PHY-2b からも確認を省いて進める。

後で復習したいこと:
- コードがアクターを動かしたことの見分け方: 体の控え(BodyEntry::pose)に「最後に伝えた・書き戻した場所」を覚え、次の同期でアクターの transform がそれと違えば、物理ではなくコードが動かしたとして SetBodyPose(瞬間移動)で伝える
- 角度を差だけ足す理由: Box2D は角度を近似の sin・cos で持つので、行って戻すと 30 度が 30.03 度になる。また -180〜180 度に丸める。そのまま写すと止まっている体でも角度が変わり、370 度が 10 度になる。体から最後に読んだ角度からの差だけを足せば、回っていない体の角度は変わらない
- 位置の向き: Dynamic は Box2D → アクター、Kinematic・Static・Rigidbody 無しはアクター → Box2D

## HIER-1: アクターの親子の階層(2026-11-14)

理解確認はスキップ(ユーザーの指示)。

後で振り返るなら:
- ワールドの行列 = 親のワールドの行列 × 自分のローカルの行列(移動 × 回転 × 拡大縮小)。点には右から効くので、まず自分のローカルの値で親から見た場所へ、次に親の行列でワールドへ運ぶ。例: 親 (100, 0)・90 度・2 倍の子 (10, 0) は、2 倍で (20, 0)、90 度で (0, 20)、移動で (100, 20)
- ワールドの値をローカルに直すときは、親のワールドの行列の逆行列を掛ける(ギズモ、SetParent で見える場所を保つとき)

## UI-1 ゲームのマウス入力(2026-11-14)

理解確認はスキップ(ユーザーの指示)。

後で振り返るなら:
- 入力の流れ: platform の`ProcessEvents`が SDL のイベントを自前の`InputEvents`(キー・マウス・画面の大きさ)に写す → `StepFrame`が`engine::Input::BeginFrame`に渡す。SDL の型は platform の外に出ないので、テストは`InputEvents`を自分で埋めるだけで同じ入力を再現できる
- ImGui が使っている間は「押した」とホイールだけ止め、「離した」と位置は渡す。離したことまで止めると、ImGui の窓の上で離したボタンがゲームの中で押されたままになる
- 画面のピクセルは y が下が +、ワールドは上が +。直すのは`FindMouseWorldPosition`(シーンのカメラで`ScreenToWorld`)
- 後のゲーム用 UI は`Input::ConsumeMouse`で、UI が使ったフレームのマウスをゲームから隠す
