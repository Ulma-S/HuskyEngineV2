# ゲームエンジン設計メモ(仮)

Nov 11, 2026

## 目的と前提

趣味と学習を目的に、個人で作るC++製ゲームエンジン。将来は「そこそこのゲームを作れる環境」を目指し、作り直しを前提にしたスクラップ&ビルド型で進める。

- 制作者: ゲームプログラマー。C++には不慣れで、C#に慣れている。
- 開発体制: まとまった時間は週末と帰宅後。移動中はスマホからClaudeに依頼するため、Claudeが自力で検証できること(テスト、ヘッドレス実行)を重視する。
- 対象: まずWindows、将来Mac。コンシューマ機は対象外。Webは保留。
- ジャンル: 未定。2Dを先行し、3Dへ拡張できる余地を残す。
- 共有: 当面は動画やスクリーンショットで共有する。

今回は勉強が主目的のため、実装は小さな単位で進め、各処理が何をしているかを理解してから次へ進む。詳細は「マイルストーンと進め方」に記載する。

## 技術スタック

全てC++で書き、ウィンドウ・入力・GPUはSDL3(SDL\_GPU)に任せる。

| 項目 | 選定 | 備考 |
| --- | --- | --- |
| 言語 | C++17。例外とRTTIは不使用 | MSVC(Visual Studio 2022)で確定 |
| ウィンドウ・入力 | SDL3 | platform層だけが触る |
| グラフィックス | SDL\_GPU | D3D12/Vulkan/Metalを共通APIで扱える。型は描画層の外に出さない |
| ビルド | CMake | 依存はvcpkgかFetchContent。パスはWindows固有にしない |
| 数学 | glmなどの既存ライブラリ | 自前では作らない |
| 開発用UI | Dear ImGui | 開発ビルドのみ |
| IDE | Visual Studio | 2022。作業フォルダは D:\\Develop\\HuskyEngineV2(プロジェクト名はHuskyEngineV2) |
| 検証 | ASan / UBSan / TSan | 常時有効にできる構成にする |

## オブジェクトモデル

ゲーム上の意味を持つものはGC管理のアクターとし、機能はコンポーネントの合成で足す。

- アクターは名前と位置を持つ薄い入れ物にする。継承は1〜2階層まで。
- 機能(見た目、体力、AIなど)はコンポーネントとして付け外しする。
- コンポーネントは`Tick`を持ち、フェーズ(入力、更新、更新後、描画前)を宣言する。
- 破棄は`Destroy()`で印を付け、フレーム末にまとめて確定する。更新中に対象が消える事故を避けるため。
- ECSは全面採用しない。大量の同質データ向けの`Pool<T>`(構造体の連続配列と世代付きハンドル)は、必要になるまで保留する。

## リフレクション

クラス単位で、プロパティ(名前・型・オフセット・参照フラグ)とメソッドをマクロで登録する。

- 用途: GCの参照追跡、シリアライズ、インスペクタの自動生成、名前からの生成、ホットリロード時の状態引き継ぎ、将来のスクリプト連携。
- M1の最小構成: 型名、プロパティ一覧、メソッド登録、オブジェクト参照フラグ。
- メソッド登録: テンプレートで関数のシグネチャを読み取り、引数配列からC++呼び出しへ変換する中継関数を自動生成する。引数と戻り値は、数値、文字列、ハンドル、GC管理オブジェクトへの参照、リフレクション対応の構造体に限る。オーバーロードは非対応。
- 登録方式: マクロで始め、記述が負担になった時点でヘッダ解析によるコード生成へ移す。

## GCとメモリ

GCは停止型のマーク&スイープで、フレーム末に破棄を確定したあと、必要なときだけ回す。

- 根(ルート): ワールド、アセットキャッシュ、明示的に登録したもの。`GC::AddRoot` / `GC::RemoveRoot`を最初から用意する。将来のスクリプト連携用で、当面は誰も呼ばない。
- 世代付きハンドル: 最初から作り、弱参照と破棄済みオブジェクトの検出に使う。
- 所有権のルール: 生の`new`/`delete`は禁止。スマートポインタ、プール、ハンドルのみを使う。
- 停止時間が問題になった場合の強化順: (1)ロード中など目立たない時だけ回す、(2)時間予算で分割して増分化する、(3)マークを並列化する。

## フレーム構造とジョブ

更新は可変dt(上限クランプ付き)を標準とし、ゲームスレッドは1本、周辺処理をジョブで並列化する。

1. 入力収集
2. 更新(フェーズ順にコンポーネントの`Tick`)
3. 破棄の確定、必要ならGC
4. 描画コマンドの構築
5. 描画の提出

- dtの決め方はゲームループの1か所に集約する。テストやリプレイでは外から固定値を注入できるようにする。物理を入れる時点で、その内部だけ固定刻みのサブステップにする。
- ジョブシステム(並列for、タスク投入)は早めに導入する(M2)。スレッド数を1にして同期実行もできる作りにする。
- アクター、コンポーネント、GC、リフレクションはゲームスレッド専用。並列化の候補は、アセットの非同期ロード、GCマークの並列化、描画コマンドの構築の順。
- 関数とクラスには、動作するスレッドを明記する。ThreadSanitizerを常時実行する。

## モジュール構成

コードはcore / engine / platform / tools / gameに分け、依存は一方向にする。

&#91;embedded content: モジュール依存 · 5モジュール\]

gameとtoolsはengineに、engineはplatformとcoreに、platformもcoreに依存する。

- core: 型、メモリ、リフレクション、GC、ハンドル、ジョブ。他のモジュールを一切知らない。単体でテストできる。
- engine: ワールド、アクター、コンポーネント、アセット、シリアライズ、入力、描画抽象。
- platform: ウィンドウ、ファイル、スレッドなどOS依存を隔離する。SDL3はここだけが触る。
- tools: ImGuiのデバッグUIとインスペクタ。engineに依存する向きだけにして、後から分離しやすくする。
- game: ゲーム固有のコード。
- ホットリロード: 最初は静的リンクで始め、M2で`game`だけをDLLに切り出す。差し替え時は、実行中のワールドを一度JSONに書き出し、新しいDLLで読み戻して状態を引き継ぐ。

## アセットとシリアライズ

アセットはGUIDで参照し、ロードは1か所のローダに集約し、保存形式はJSONから始める。

- 参照: `AssetRef<T>`(中身はGUID)で参照し、GUIDとパスの対応表を持つ。
- 元データ: PNGやglTFなどをそのまま読む。ローダ内部を「元ファイルを読む」「実行用データにする」の2段に分け、2段目は最初は素通しにする。将来のネイティブコンバートは2段目を差し替えて入れ、結果は元ファイルのハッシュと変換器の版をキーにキャッシュする。個人的な興味として、いずれ導入したい。
- シリアライズ: リフレクションの走査を「アーカイブ」インターフェース越しに行う。JSONはその実装の1つで、ネットワーク用などの別シリアライザは実装を足して対応する。
- 非同期ロードの備え: `Load(guid)`は必ずハンドル(読み込み中、完了、失敗)を返す。最初は呼んだ時点で読み終える同期実装にする。内部は「バイト列からデータへの変換」と「オブジェクトの生成」に分け、前者を将来ワーカーに回せるようにする。
- GCとの関係: アセットはGC管理で、キャッシュは弱参照にする。読み込み中のアセットは根として保持する。

## レンダラ

SDL\_GPUを薄い自前の層で隠し、ゲーム側は描画コマンドを積むだけにする。

- 公開するのは`RenderDevice`インターフェースと、エンジン独自の型(`Texture`、`Buffer`、`Pipeline`など)だけ。SDL\_GPUの型は実装クラスの外に出さない。後からVulkanやD3D12の直接実装、WebGPUに差し替えられる。
- 描画コマンドは更新後は読み取り専用にして、将来の描画スレッド分離に備える。2Dはスプライトのバッチ描画から始め、3Dは後から足す。
- GPUリソースは世代付きハンドルで管理する。GPUはCPUより1〜3フレーム遅れて動くため、GCがアセットを回収しても、GPUリソースはすぐ解放せず遅延解放キューに入れる。同時に溜め込むフレーム数(通常2〜3)を待ってから解放する。
- シェーダは1つの記述から各API形式へ変換する流れが必要。変換ツールの現状は、着手時に調べ直す。

## UIとツール

開発用UI(ImGui)とインゲームUIは、完全に別系統として扱う。

- 開発用: ImGuiでインスペクタ(リフレクションから自動生成)、ワールド階層、GCとメモリの統計、フレーム時間のグラフを作る。リリースビルドではコードごと外す。ImGuiが入力を使用中は、ゲームに渡さない。本格的なシーンエディタは作らず、シーンはJSONで編集してホットリロードで確認する。
- インゲームUI: 将来、RmlUiなどの高機能なUIフレームワークに載せる想定。着手時に最新の状況を確認する。備えは3つ。UIも描画コマンド経由で描く。入力はエンジンの入力層で一元管理し、UIが消費したらゲームに渡さない。データはリフレクション経由でバインドする。

## 保留事項と将来拡張

以下は今は作らず、差し込み口だけを残す。

| 項目 | 現状 | 再開の目安 |
| --- | --- | --- |
| スクリプト言語やC#の連携 | 保留。メソッド登録、ハンドル経由のアクセス、根の登録口を用意しておく | 必要になった時 |
| Web(WASM)対応 | 保留。SDL\_GPUのブラウザ対応が不明なため、描画層の差し替えが必要になる見込み。.NETのWASM対応(CoreCLR化)は.NET 12頃に固まる見込み | M3以降に小さなサンプルで検証 |
| `Pool<T>` | 保留 | 大量の同質オブジェクトが必要なジャンルに決まった時 |
| コード生成リフレクション | 保留。マクロ登録で開始 | 記述が負担になった時 |
| 3D | 描画抽象は3D対応可能な形にする。実装は2D後 | 2D完成後。メッシュ、glTF、基本ライティングで追加数週間が目安 |
| ネットワーク | 保留。アーカイブ抽象と同期フラグの余地を残す | 対戦要素が必要になった時 |
| ネイティブコンバート | 保留。ローダの2段構成で差し込み口を確保 | 起動時間が気になった時、または興味で着手 |
| 非同期ロード | APIは対応済み。実装は同期 | ロード待ちが気になった時 |
| 増分GC、並列GC | 保留 | GC停止が目立つ時 |
| Mac対応 | 設計は塞がない。OS依存はplatform層に隔離 | Windowsが安定した後 |

## マイルストーンと進め方

M0〜M3の4段階で進め、各段階を30分〜1時間の小さなステップに分けて、1ステップごとに理解を確認してから次へ進む。

&#91;embedded content: マイルストーン · M0〜M3\]

M2までは機能を作る段階で、M3で実際のゲームを作りながら、エンジンに足りないものを洗い出す。

- M0: ウィンドウ、ゲームループ、入力、スプライト描画。
- M1: オブジェクトシステム(基底クラス、世代付きハンドル、プロパティとメソッドのリフレクション、GC)とテスト。
- M2: JSONシリアライズ、アセット(GUID、ローダ)、ジョブシステム、ImGuiのデバッグUI、`game`のDLL化によるホットリロード。
- M3: ミニゲーム1本を作り、ジャンルをここで決める。不足する機能を作りながら抽出する。

学習方針は次の通り。この設計メモと`CLAUDE.md`の両方に記載する。

1. 実装は細かい単位で進め、各ステップで「何をしているか」と「なぜそうするか」を先に説明する。
2. ステップが終わるたびに、理解できたかを確認する。確認が取れてから次へ進む。
3. 理解を一時的にスキップすると言われた間は、確認を省いて先へ進んでよい。スキップした範囲は記録しておき、後で振り返れるようにする。
