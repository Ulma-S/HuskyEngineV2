# ゲームエンジン設計メモ(仮)

Nov 11, 2026

## 目的と前提

趣味と学習を目的に、個人で作るC++製ゲームエンジン。将来は「そこそこのゲームを作れる環境」を目指し、作り直しを前提にしたスクラップ&ビルド型で進める。

- 制作者: ゲームプログラマー。C++には不慣れで、C#に慣れている。
- 開発体制: まとまった時間は週末と帰宅後。移動中はスマホからClaudeに依頼するため、Claudeが自力で検証できること(テスト、ヘッドレス実行)を重視する。
- 対象: まずWindows、将来Mac。コンシューマ機は対象外。Webは保留。
- ジャンル: 未定。2Dを先行し、3Dへ拡張できる余地を残す。
- 共有: 当面は動画やスクリーンショットで共有する。

今回は勉強が主目的のため、実装は小さな単位で進め、各処理が何をしているかを理解してから次へ進む。詳細は「マイルストーンと進め方」に記載する。

## オブジェクトモデル

ゲーム上の意味を持つものはGC管理のアクターとし、機能はコンポーネントの合成で足す。

- アクターは名前と位置を持つ薄い入れ物にする。継承は1〜2階層まで。
- 機能(見た目、体力、AIなど)はコンポーネントとして付け外しする。
- コンポーネントは`Tick`を持ち、実行順(整数、UnityのDefaultExecutionOrderにあたる)を宣言する。よく使う値には名前を付ける(入力 -1000、既定 0、更新後 1000、描画前 2000)。`LateUpdate`のような別の関数は作らず、順番だけで表す。(2026-11-12、フェーズの列挙から変更。間の値で細かく順番を決められるようにするため)
- 破棄は`Destroy()`で印を付け、フレーム末にまとめて確定する。更新中に対象が消える事故を避けるため。
- ECSは全面採用しない。大量の同質データ向けの`Pool<T>`(構造体の連続配列と世代付きハンドル)は、必要になるまで保留する。

## リフレクション

クラス単位で、プロパティ(名前・型・オフセット・参照フラグ)とメソッドをマクロで登録する。

- 用途: GCの参照追跡、シリアライズ、インスペクタの自動生成、名前からの生成、ホットリロード時の状態引き継ぎ、将来のスクリプト連携。
- M1の最小構成: 型名、プロパティ一覧、メソッド登録、オブジェクト参照フラグ。
- メソッド登録: テンプレートで関数のシグネチャを読み取り、引数配列からC++呼び出しへ変換する中継関数を自動生成する。引数と戻り値は、数値、文字列、ハンドル、GC管理オブジェクトへの参照、リフレクション対応の構造体に限る。オーバーロードは非対応。
- 登録方式: マクロで始め、記述が負担になった時点でヘッダ解析によるコード生成へ移す。
- 構造体(2026-11-12): `Object`ではない値の構造体も、型の外から登録できる(`HUSKY_STRUCT_BEGIN`)。外部ライブラリの型や、ほかのモジュールの型(例: `render::Color`をengineの側で登録)にも使える。プロパティにすると、保存は入れ子になり、中のハンドルはGCがたどる。構造体の配列や、メソッドの引数として使うのは、必要になったら足す。

## GCとメモリ

GCは停止型のマーク&スイープで、フレーム末に破棄を確定したあと、必要なときだけ回す。

- 根(ルート): ワールド、アセットキャッシュ、明示的に登録したもの。`GC::AddRoot` / `GC::RemoveRoot`を最初から用意する。将来のスクリプト連携用で、当面は誰も呼ばない。
- 世代付きハンドル: 最初から作り、弱参照と破棄済みオブジェクトの検出に使う。
- 所有権のルール: 生の`new`/`delete`(と`malloc`/`free`)は禁止。スマートポインタ、プール、ハンドルのみを使う。
- 停止時間が問題になった場合の強化順: (1)ロード中など目立たない時だけ回す、(2)時間予算で分割して増分化する、(3)マークを並列化する。

### メモリの確保の方針(2026-11-12 の相談で決めた想定)

基本の考え方: **どの確保も、エンジンが握る入口を通す(追跡できる)。実体のアロケータは、寿命と大きさで選ぶ。**

- 入口を握る目的は2つ。(1)追跡(どこがどれだけ使っているか。性能改善の前提になる)、(2)後からの差し替え(遅い場所だけ専用のアロケータに替える。アプリ層のコードは変えない)。
- `malloc`は「OSから直接」ではない。OSから大きな塊を借りて切り分ける汎用のアロケータで、OSを呼ぶのはたまにだけ。汎用のアロケータの弱点は、ロックの取り合い、断片化、局所性の悪さ、1回ごとの手間。
- 専用のアロケータは、寿命か大きさを揃えることで、断片化を減らし、速くする(空きを探さない、近くに並ぶ、予算と追跡が分かれる、スレッドごとに持てばロックが要らない)。使い方が分かっていて効果が大きい場所だけに使う。何でも1つの自作アロケータに入れると、汎用のアロケータと同じ悩みを抱える。
- 専用のアロケータの中の誤用はASanから見えない。対策は(1)ポイズニングを入れる、(2)ASanのビルドでは実体を標準の`malloc`に切り替える。

アロケータの一覧(想定):

| | アロケータ | 入れるもの | 寿命 | 状態 |
|---|---|---|---|---|
| 1 | GCのヒープ(`FreeListAllocator`) | ゲームオブジェクト(`Object`の子孫) | 長い、ばらばら | ある。ASanのポイズニングを入れる |
| 2 | 汎用のヒープ(`operator new`を差し替えて数え、`malloc`へ) | コンテナの中身、`std::string`、`make_unique`したものなど、その他すべて | 何でも | 次の候補 |
| 3 | フレームアロケータ(線形) | 1フレームだけ使う一時的なもの(描画コマンド、順番表など) | フレームの終わりに一括で捨てる | 必要になったら |
| 4 | プール(`Pool<T>`) | 同じ大きさのものを大量に(弾、パーティクル) | 個別だが大きさが同じ | 保留 |
| 5 | GPUのメモリ | テクスチャ、バッファ | 世代付きハンドル。解放は数フレーム遅らせる | renderの中 |
| 6 | アセット | 読み込んだファイルの中身 | ロードからアンロードまで | M2で決める |
| 7 | スレッドごとの一時領域 | ジョブの中の一時的なもの | ジョブの間 | M2で決める |
| 8 | 外部ライブラリ | SDL、ImGuiなどの内部の確保 | — | 差し替え口(`SDL_SetMemoryFunctions`、`ImGui::SetAllocatorFunctions`)から2の入口へ流す |

アプリ層(ゲームのコード)から見た使い分け:

| やりたいこと | 書き方 | 使われるアロケータ |
|---|---|---|
| ゲームオブジェクトを作る | `Scene::Spawn` / `Actor::AddComponent` | 1 |
| 普通のオブジェクトをいつも持つ | メンバーに値で持つ(`new`しない。親の中に埋め込まれる) | 親と同じ場所 |
| 普通のオブジェクトを後から作る、差し替える、継承を使う | `std::make_unique`(持ち主1人)。複数なら`std::make_shared` | 2 |
| 同じものを複数 | `std::vector<T>`など | 2 |
| テクスチャや音を使う | ハンドル(`AssetRef<T>`など)で持つ | 5、6 |
| 速さが要る一時的なもの、大量の同じもの | エンジンが渡すフレーム用のコンテナ、`Pool<T>`(計測して遅いと分かってから) | 3、4、7 |

- 普段はアロケータを意識しない。速さが要る場所だけ、自分で選ぶ。
- 生の`new`/`delete`と`malloc`/`free`は書かない。理由は所有権の安全(誰が解放するかが読める、漏れや二重解放を防ぐ)。追跡は入口(2)で守る。
- 注意: `Object`の子孫ではない普通のオブジェクトの中の`ObjectHandle`は、GCから見えない(弱い参照になる)。相手を生かしておきたいなら、`Object`の子孫のプロパティとして持つ。将来、UEの`FGCObject`や`TStrongObjectPtr`にあたる道具が要るかもしれない。
- 仕組みごとに使用量を分けて見たくなったら、確保に名札を付ける(例: `MemoryScope scope("AI");`。UEのLLMの`LLM_SCOPE`にあたる)。

追跡の範囲:

| 範囲 | 方法 |
|---|---|
| 自分のコードの`new` | `operator new`の差し替え |
| 自分のコードの`malloc` | 使わないルール + エンジンの確保の関数 |
| SDL、ImGuiなど | ライブラリの差し替え口から入口へ流す |
| それ以外(ドライバ、差し替え口の無いライブラリ) | OSが報告するプロセス全体の量(Windowsは`GetProcessMemoryInfo`。platformに置く)との差を「追跡できていない分」として出す(UEのLLMの「Untracked」と同じ考え方) |
| 詳しい調査 | Visual Studioの診断ツール、Windows Performance Analyzer(ETWのヒープ追跡)、Tracyなど |

参考(UEとの対応): `UObject`を`NewObject`で作りGCで消す(このエンジンの1)、`UPROPERTY`が強い参照、`TUniquePtr`/`TSharedPtr`/`TArray`は全モジュールで差し替えた`operator new`から`FMemory`(`FMalloc`、既定は大きさごとの箱に分けるBinned系)へ流れる。ASanのビルドでは標準の`malloc`に切り替える。UEでは普通のクラスの生の`new`/`delete`は書けるが、`UObject`には使えない。生の`new`を避ける理由は追跡ではなく所有権。

## フレーム構造とジョブ

更新は可変dt(上限クランプ付き)を標準とし、ゲームスレッドは1本、周辺処理をジョブで並列化する。

1. 入力収集
2. 更新(実行順にコンポーネントの`Tick`)
3. 破棄の確定、必要ならGC
4. 描画コマンドの構築
5. 描画の提出

- dtの決め方はゲームループの1か所に集約する。テストやリプレイでは外から固定値を注入できるようにする。物理を入れる時点で、その内部だけ固定刻みのサブステップにする。
- ジョブシステム(並列for、タスク投入)は早めに導入する(M2)。スレッド数を1にして同期実行もできる作りにする。
- アクター、コンポーネント、GC、リフレクションはゲームスレッド専用。並列化の候補は、アセットの非同期ロード、GCマークの並列化、描画コマンドの構築の順。
- 関数とクラスには、動作するスレッドを明記する。ThreadSanitizerを常時実行する(Mac対応後。Windowsでは使えないため。それまでに複数スレッドを使うなら扱いを相談する)。

## モジュール構成

コードはcore / engine / platform / tools / gameに分け、依存は一方向にする。

gameとtoolsはengineに、engineはplatformとcoreに、platformもcoreに依存する。

- core: 型、メモリ、リフレクション、GC、ハンドル、ジョブ。他のモジュールを一切知らない。単体でテストできる。
- engine: ワールド、アクター、コンポーネント、アセット、シリアライズ、入力、描画抽象。
- platform: ウィンドウ、ファイル、スレッドなどOS依存を隔離する。SDL3はここだけが触る。
- tools: ImGuiのデバッグUIとインスペクタ。engineに依存する向きだけにして、後から分離しやすくする。
- game: ゲーム固有のコード。
- ホットリロード: 最初は静的リンクで始め、M2で`game`だけをDLLに切り出す。差し替え時は、実行中のワールドを一度JSONに書き出し、新しいDLLで読み戻して状態を引き継ぐ。

## アセットとシリアライズ

アセットはGUIDで参照し、ロードは1か所のローダに集約し、保存形式はJSONから始める。

- 参照: `AssetRef<T>`(中身はGUID)で参照し、GUIDとパスの対応表を持つ。
- アセットのフォルダ(2026-11-12にユーザーと決定): 開発ビルドは、ソースの`assets`を直接読み書きする。製品は、ビルドで別に用意したもの(今はexeの隣へのコピー、将来は変換して固めたもの)を読むだけ。Unity(`Assets`、取り込み結果は`Library`)、UE(`Content`、製品は変換した`.pak`)、Godot(`res://`、製品は`.pck`)と同じ分け方。これで、足した・直したファイルがビルドし直さずに見え、エディタが書くもの(シーン、`.meta`)も1か所で済む。
- 元データ: PNGやglTFなどをそのまま読む。ローダ内部を「元ファイルを読む」「実行用データにする」の2段に分け、2段目は最初は素通しにする。将来のネイティブコンバートは2段目を差し替えて入れ、結果は元ファイルのハッシュと変換器の版をキーにキャッシュする。個人的な興味として、いずれ導入したい。
- シリアライズ: リフレクションの走査を「アーカイブ」インターフェース越しに行う。JSONはその実装の1つで、ネットワーク用などの別シリアライザは実装を足して対応する。
- 非同期ロードの備え: `Load(guid)`は必ずハンドル(読み込み中、完了、失敗)を返す。最初は呼んだ時点で読み終える同期実装にする。内部は「バイト列からデータへの変換」と「オブジェクトの生成」に分け、前者を将来ワーカーに回せるようにする。
- GCとの関係: アセットはGC管理で、キャッシュは弱参照にする。読み込み中のアセットは根として保持する。
- 非同期ロード(2026-11-12時点): 実装済み。ファイルを読む・実行用データにする段はジョブ(ワーカー)で行い、結果をアセットに書くのはゲームスレッド(`AssetLoader::Update`)。読み込み中のアセットは根にせず、読み込み中の記録が弱参照で指す(回収されていたら結果を捨てる)。
- テクスチャとスプライトシート(2026-11-12にユーザーと決定):
  - テクスチャは「画像 + `.meta`」をそのままアセットにする(1枚の画像 = 1つのテクスチャ。Unityと同じ形)。`.meta`は「元の画像をどう取り込むか」(インポートの設定)の置き場所。
  - 切り出し(スプライトシート)は、自分で作るデータとして、画像を包む別のアセット(`.spritesheet`、JSON)にする。画像はGUIDで指す。1枚の画像を、テクスチャとして直接使いながら、いくつものスプライトシートからも使える。どれも同じGUIDのテクスチャなので、画像は1回だけ読む。
  - 切り出しは「スプライトシートのGUID + 切り出しのID」で指す。IDは0以外のint32の乱数で、一度振ったら変えない(名前は表示用)。
- テクスチャを包むアセットへの移し替え(将来の拡張の余地として残す): 同じ画像を別々の取り込みの設定(圧縮、ミップマップ、色の扱い)で使いたくなったら、テクスチャも画像を包むアセット(`.texture`のようなファイル。中で元の画像を指す)にする(Unrealの形)。そのとき、シーンやスプライトシートが今指している「画像のGUID」の扱いを決める必要がある。案: 最初に作る包むアセットに、画像の`.meta`のGUIDを引き継がせ、画像の`.meta`には新しいGUIDを振り直す(指していた側は、何も直さずに包むアセットを指すことになる)。フィルタ(最近傍かなめらかか)だけなら、テクスチャを分けずに、描くときのサンプラーの選択で対応できる。
- シーンのファイルの中の参照(2026-11-12時点): オブジェクト同士はファイルの中だけの番号で指し合い、保存のたびに0から振り直す(`SceneSerializer`)。ファイルの外(アセット)を指すときだけGUIDを使う(Unityの`fileID`と`guid`の2段構えと同じ考え方)。弱点は、オブジェクトを足し引きすると番号がずれて差分が大きくなること、ほかのファイルからシーンの中のオブジェクトを指せないこと。アセットやプレハブを作るときに、オブジェクトごとに保存しても変わらない番号を持たせる方式を検討する。

## レンダラ

SDL\_GPUを薄い自前の層で隠し、ゲーム側は描画コマンドを積むだけにする。

- 公開するのは`RenderDevice`インターフェースと、エンジン独自の型(`Texture`、`Buffer`、`Pipeline`など)だけ。SDL\_GPUの型は実装クラスの外に出さない。後からVulkanやD3D12の直接実装、WebGPUに差し替えられる。
- 描画コマンドは更新後は読み取り専用にして、将来の描画スレッド分離に備える。2Dはスプライトのバッチ描画から始め、3Dは後から足す。
- GPUリソースは世代付きハンドルで管理する。GPUはCPUより1〜3フレーム遅れて動くため、GCがアセットを回収しても、GPUリソースはすぐ解放せず遅延解放キューに入れる。同時に溜め込むフレーム数(通常2〜3)を待ってから解放する。
- シェーダは1つの記述から各API形式へ変換する流れが必要。変換ツールの現状は、着手時に調べ直す。

## UIとツール

開発用UI(ImGui)とインゲームUIは、完全に別系統として扱う。

- 開発用: ImGuiでインスペクタ(リフレクションから自動生成)、ワールド階層、GCとメモリの統計、フレーム時間のグラフを作る。リリースビルドではコードごと外す。ImGuiが入力を使用中は、ゲームに渡さない。
- エディタの形(2026-11-12に決定): 最初は、エディタの機能(配置、インスペクタ、シーンの保存)を開発ビルドのゲームと同じプロセスに組み込み(`tools`モジュール)、製品のビルドでは抜く。UnityやUEのエディタと同じく、エディタはエンジンそのものの上で動く。いずれ、エディタを別のプロセスにして、ゲームとプロセス間通信でつなぐ形も検討する(そのために、エディタの操作はエンジンへの「コマンド」として表し、直接オブジェクトを書き換える経路を増やしすぎない)。別のプロセスにする一番の利点は、ゲーム(ランタイム)がクラッシュしても、エディタ側の編集中のデータが失われないこと。同じプロセスの間は、保存を「一時ファイルに書いてから置き換える」形にして、保存の途中のクラッシュで元のファイルが壊れないようにする。
- AIから使いやすいエディタ(2026-11-12にユーザーと相談): エディタの操作(アセットを作る、プロパティを書き換える、保存する、調べる)は、画面から切り離した「エディタのコマンド」(名前と引数を持つ操作)として1か所に作る。ImGuiのボタン、コマンドラインツール、MCPサーバ(AIから使う)は、どれもこのコマンドを呼ぶだけの薄い入口にする。人もAIも同じ道を通るので、決まり(GUIDやIDを振る、`.meta`を作る、形を確かめる)が必ず守られる。Undoもコマンドの単位で作る。
  - 順番の目安: (1)コマンドの層 → (2)コマンドラインツール(ファイルを相手にする1回ずつの操作、CIでの確認) → (3)エディタを別のプロセスにするときに、同じプロセス間通信の口にMCPをかぶせる(動いているゲームへの問い合わせと操作)。着手は、エンジンとアプリ(ゲーム)を切り分けるとき。
  - 人も使う(2026-11-12にユーザーの要望): コマンドは機械向けの名前のほかに、人向けの表示名、説明(ツールチップ。AIへの説明にも使う)、ショートカットを持つ。結果は、人が読む1行の要約と細かい内容に分け、画面(成功は緑、失敗は赤)とログの両方に出す。最初の1段目(コマンドの形と一覧、`scene.save`)は作り済み(`tools/EditorCommands.h`)。
  - 今のうちから守ること: エディタの操作をImGuiの中に直接書かず、関数として外に置く(`SaveSceneFile`、`NormalizeSpriteSheetsInFolder`はこの形)。報告は「数と理由の一覧」で返し、後でJSONでも出せるようにする。調べる操作(アセットの一覧、参照元、型とプロパティの一覧)も、作る操作と同じくらい大事にする。
  - 既にある土台: リフレクション(コマンドの引数の形や、MCPのツールの説明を自動で作れる)、テキストで差分が読みやすいファイル(JSON、メンバーの順番を保つ)、変わらないID(GUID、切り出しのID)、画面なしで結果が毎回同じに動かせること(`StepFrame`)。
- 役目の分け方: シーンのファイルを保存するのはエディタ(開発ビルドだけ)。製品のゲームは読み込むだけ。セーブデータ(プレイヤーの進行)の保存は、これとは別の仕組みとして扱う。
- インゲームUI: 将来、RmlUiなどの高機能なUIフレームワークに載せる想定。着手時に最新の状況を確認する。備えは3つ。UIも描画コマンド経由で描く。入力はエンジンの入力層で一元管理し、UIが消費したらゲームに渡さない。データはリフレクション経由でバインドする。

## 保留事項と将来拡張

以下は今は作らず、差し込み口だけを残す。

| 項目 | 現状 | 再開の目安 |
| --- | --- | --- |
| スクリプト言語やC#の連携 | 保留。メソッド登録、ハンドル経由のアクセス、根の登録口を用意しておく。スクリプトで定義した型の保存は、(1)C++の入れ物のコンポーネントがスクリプトのフィールドを走査して`ArchiveValue`に書く(Unity型)か、(2)実行中に`TypeInfo`を作り、関数で読み書きするプロパティを足す(UEのBlueprint型)。そのため、プロパティの読み書きは`Property`に集めてある | 必要になった時 |
| Web(WASM)対応 | 保留。SDL\_GPUのブラウザ対応が不明なため、描画層の差し替えが必要になる見込み。.NETのWASM対応(CoreCLR化)は.NET 12頃に固まる見込み | M3以降に小さなサンプルで検証 |
| `Pool<T>` | 保留 | 大量の同質オブジェクトが必要なジャンルに決まった時 |
| コード生成リフレクション | 保留。マクロ登録で開始 | 記述が負担になった時 |
| 3D | 描画抽象は3D対応可能な形にする。実装は2D後 | 2D完成後。メッシュ、glTF、基本ライティングで追加数週間が目安 |
| 編集モード(Play / Stop。2026-11-12にユーザーと相談) | 今は常に再生中(毎フレーム`Scene::Tick`を呼ぶ)。作るときは、編集(Tickを呼ばない)・再生・一時停止(コマ送りも)の状態を持ち、描画、アセットの読み込み、GC、開発用のUIはどの状態でも動かす。Playでシーンをメモリの`ArchiveValue`に保存し、Stopでそこから読み直して編集の状態に戻す(Unityと同じ。再生中の変更は消える)。PlayとStopもエディタのコマンドにする。開発ビルドだけ。編集中も動かしたいコンポーネント(アニメーションのプレビューなど)の印は、要るときに足す | 作り済み(2026-11-12、ED-3。`tools/EditorPlayMode.h`)。編集中も動かしたいコンポーネントの印と、Playのショートカットのキーは、まだ無い |
| エンジンのモジュール化(付け外し。2026-11-12にユーザーと相談) | 今はCMakeの静的ライブラリ(core / platform / render / engine / tools)で、付け外しできるのはtools(開発ビルドだけ)だけ。2D(スプライト、スプライトシート、アニメーション)はengineに直接入っている。作るときは、(1)モジュールの形(名前、依存、開始と終了。開始で型、アセットの種類、描画の処理、インスペクタの表示を登録する。UEのモジュールやGodotの`register_types`と同じ考え)、(2)差し込み口(アセットの種類を登録で足せるローダ、登録された順に呼ぶ描画の処理)、(3)2Dを1つ目のモジュールとして切り出す、(4)CMakeの選択肢(`HUSKY_WITH_SPRITE2D`など)でライブラリごと付け外す。実行中の付け外し(DLL)はホットリロードと一緒に考える | 2つ目の大きなカテゴリ(音、物理、3D)を足す時に、それを最初からモジュールとして作り、2Dも移す。アセットの種類を登録で足せるローダは、それより早くてもよい |
| アニメーションの共通化(2026-11-12にユーザーと相談) | 今はスプライト専用(`SpriteAnimatorComponent`。切り出しのIDを時間で切り替える)。骨のアニメーション(FBXなど)は、値の種類(とびとびのIDと、補間する骨の姿勢)も、要る機能(混ぜ合わせ、状態の切り替え、GPUでの変形)も違うので、別の仕組みにする。汎用の名前`Animator`は空けておく。共通にできる候補は2つ。(1)再生の状態(経った時間、速さ、ループ、再生中か)を小さな構造体に切り出して両方で使う。(2)UnityやGodotのAnimationPlayerのような「どのプロパティでも時間で書き換える」汎用のプロパティアニメーション(リフレクションがあるので向いている)。FBXの読み込みには新しいライブラリが要るので、着手の前に相談する | 3Dのアニメーションに着手する時、または汎用のプロパティアニメーションが欲しくなった時に検討する |
| ネットワーク | 保留。アーカイブ抽象と同期フラグの余地を残す | 対戦要素が必要になった時 |
| ネイティブコンバート | 保留。ローダの2段構成で差し込み口を確保 | 起動時間が気になった時、または興味で着手 |
| 非同期ロード | APIは対応済み。実装は同期 | ロード待ちが気になった時 |
| 増分GC、並列GC | 保留 | GC停止が目立つ時 |
| Mac対応 | 設計は塞がない。OS依存はplatform層に隔離 | Windowsが安定した後 |

## マイルストーンと進め方

M0〜M3の4段階で進め、各段階を30分〜1時間の小さなステップに分けて、1ステップごとに理解を確認してから次へ進む。

&#91;embedded content: マイルストーン · M0〜M3\]

M2までは機能を作る段階で、M3で実際のゲームを作りながら、エンジンに足りないものを洗い出す。

- M0: ウィンドウ、ゲームループ、入力、スプライト描画。
- M1: オブジェクトシステム(基底クラス、世代付きハンドル、プロパティとメソッドのリフレクション、GC)とテスト。
- M2: JSONシリアライズ、アセット(GUID、ローダ)、ジョブシステム、ImGuiのデバッグUI、`game`のDLL化によるホットリロード。
- M3: ミニゲーム1本を作り、ジャンルをここで決める。不足する機能を作りながら抽出する。

学習方針は次の通り。この設計メモと`CLAUDE.md`の両方に記載する。

1. 実装は細かい単位で進め、各ステップで「何をしているか」と「なぜそうするか」を先に説明する。
2. ステップが終わるたびに、理解できたかを確認する。確認が取れてから次へ進む。
3. 理解を一時的にスキップすると言われた間は、確認を省いて先へ進んでよい。スキップした範囲は記録しておき、後で振り返れるようにする。
